feat(kmod): rewrite init_uts_ns so uname(2) reports a handset, system-wide (107 -> 110 tools)

`uname` was the one tell that neither `resetprop` nor a bind mount could reach, because it
reads a kernel struct rather than a file. The fix is an out-of-tree module that rewrites
`init_uts_ns.name` — the single struct every `uname` copies from.

Measured across every path a check reads:

  before: 6.1.90-perf+
  after : 6.1.75-android14-11-g4d9e0d1b2c3f

`uname -r`, `uname -m`, `uname -a`, /proc/sys/kernel/osrelease, /proc/version and a freshly
spawned shell all agree; `rmmod` restores them. It also loads from the KernelSU module's
service.sh, so it survives a reboot (verified by rebooting).

## Why the obvious approach cannot work

The 6.1.90 source says it outright, in arch/x86/entry/syscall_64.c:

    /*
     * The sys_call_table[] is no longer used for system calls, but
     * kernel/trace/trace_syscalls.c still wants to know the system call address.
     */
    const sys_call_ptr_t sys_call_table[] = { ... };

    long x64_sys_call(const struct pt_regs *regs, unsigned int nr)
    {
            switch (nr) { case 63: return __x64_sys_newuname(regs); ... }
    }

Dispatch is that switch, called from arch/x86/entry/common.c. Writing sys_call_table[63]
changes a table nothing reads — which is why a module that poisoned all 55 slots of
`struct module` still loaded cleanly and changed nothing. And set_memory_rw, needed to make
that table writable, takes cpa_lock and flushes the TLB; calling it from module init wedged
the guest hard enough that adb and the manager channel both stopped answering.

`init_uts_ns` sidesteps all of it: it is exported (__ksymtab_init_uts_ns is in kallsyms) and
sits at 0xffffffff8a7b43d0, past __end_rodata (0xffffffff8a494000), i.e. in ordinary
writable data. The module references it directly and writes it with a plain store — no
address patching, no code patching, nothing that varies per boot.

Also settled from source: `uname` is number 63 and its handler is newuname
(syscall_64.tbl), which two kprobes confirmed at runtime — 3 hits for __x64_sys_newuname,
0 for __x64_sys_uname over three uname calls.

## Building it on Windows

The module must match `uname -r` exactly: AOSP `deprecated/android14-6.1-2024-08`, whose
Makefile says SUBLEVEL = 90 (commit ab81bbc79). native/km/README.md records the full recipe
and every obstacle. The one worth naming here: a `fixdep` stub that wrote to argv[2]
truncated every object file to zero bytes — argv[2] is the target .o, not the command file —
which made modpost report "Invalid argument" on an empty ELF and hid the real problem for a
long time.
