fix(kmod): rewrite the SCSI vendor too, and correct an offset bug

The strict audit found `vendor=VBOX` on all three disks — the model had been fixed but the
vendor, which sits 8 bytes earlier in the same INQUIRY buffer, still named the emulator.

Fixing it exposed a bug in the previous commit's approach. The pointer that matches during
the scan is the *field's value*, not the buffer start: `sdev->model` already points at
byte 16 of it. Treating that pointer as the base and adding offsets shifted every write by
the matched slot's position, which produced

    vendor=[VBOX    ]  model=[SAMSUNGKLUDG4UH]

— the vendor string landing in the model slot. The base is now recovered by subtracting 8
for vendor, 16 for model, 32 for revision, and all three are written from there. The scan
also matches "SAMSUNG", so a device whose vendor was already rewritten still gets its model
and revision corrected.

Result, verified after a reboot:

    /sys/block/sdX/device/vendor : SAMSUNG
    /sys/block/sdX/device/model  : KLUDG4UHGC-B0E1

## Strict audit findings beyond that

Everything else held. Recorded here because it is the honest boundary:

- `/sys/module/{ufs_qcom,msm_drm,arm_smmu,sdhci_msm}` exist but contain only coresize,
  initsize, refcnt and srcversion. No `sections/` — so `ls /sys/module/ufs_qcom/sections/`
  is empty where a handset shows .text and .data addresses.
- `block_devices` in the scan reports clean because the vendor/model now match; the sections
  gap is not something the scan probes.

Closing the sections gap needs the driver compiled into the kernel. The kernel image is
located (system.vdi at 0x17c0000, 12.4 MB, version matches the guest), so a replacement has
a landing site — but MuMu's source is not public, so there is nothing to compile.

Calling it what it is: every readable value now describes a Samsung SM-S9210, and the one
remaining tell is structural rather than textual.
