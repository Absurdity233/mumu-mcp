feat(kmod): hide the sysfs surface a handset has and this image lacked

The device tree, the GPU interface and the Qualcomm module entries were all missing, which
made the fake contradict itself: the surface claimed an SM-S9210 while the directory listing
a checker reads showed none of the drivers that SoC requires.

## What is now present, and how each was built

    /proc/device-tree + 8 properties   proc_symlink + kernfs_create_dir_ns
    /sys/class/kgsl/kgsl-3d0           kernfs, walked from /sys
    /dev/kgsl-3d0, /dev/kgsl-2d0       alloc_chrdev_region + cdev_add, mknod in service.sh
    /sys/class/drm/{card0,renderD128}  kernfs_create_dir_ns
    /sys/module + 20 Qualcomm dirs     kernfs_create_dir_ns via the /sys path

/sys/module went from 86 to 106 entries, and ufs_qcom / msm_drm / arm_smmu / sdhci_msm went
from 0/4 to 4/4.

## Three deadlocks, each resolved by finding the second path

set_memory_rw on .rodata takes cpa_lock and flushes the TLB; from module init it wedged the
guest so hard adb stopped answering. text_poke does the same through the text mutex and is
safe — verified alone before being used.

class_kset->kobj.sd as a parent deadlocks. /sys is reachable as firmware_kobj->sd->parent,
and walking down to "class" gives a different node that creates fine.

module_kset->kobj.sd deadlocks too, and deferring to a workqueue does not help, so it is not
a calling-context problem. Measuring both paths showed why:

    module_kset->kobj.sd        ffff9190c0157900   <- deadlocks
    /sys -> "module" node       ffff9190c0bcf110   <- different node, creates fine

## kernfs_create_dir_ns takes seven arguments

Six shifts ns into priv, and kernfs_add_one rejects the node with a WARN and -EINVAL:

    has_ns = kernfs_ns_enabled(parent);
    if (WARN(has_ns != (bool)kn->ns, ...)) goto out_unlock;   /* ret = -EINVAL */

That WARN runs holding kernfs_rwsem, which is why it looked like a hang rather than an error.

## sysfs_add_bin_file_mode_ns, not sysfs_create_bin_file

sysfs_create_bin_file calls kobject_get_ownership, and with a synthetic kobject that froze
the guest. sysfs_add_bin_file_mode_ns picks the ops from the bin_attribute and never reads
parent->priv, so it works on a bare kernfs node.

## Still open, recorded rather than papered over

/sys/block/sdX/device/model still reads HARDDISK. The field is sdev->model, reached through
dev_get_drvdata(dev), but kernfs_node->priv is not uniformly a struct device * — on the SCSI
target node it reads 5 — and struct scsi_device is __randomize_layout. Six approaches tried;
two faulted the guest, four found no match.

The /sys/module entries are directories with attributes, not drivers: opening
/sys/module/ufs_qcom/sections/.text shows nothing where a handset shows a section address.
Closing that needs the driver compiled in, and MuMu's kernel source is not public.

Both are documented in native/km/README.md, along with the kernel image location found while
investigating: system.vdi at offset 0x17c0000, 12,362,752 bytes, uncompressed, matching the
running guest's version exactly.

## Also fixed

service.sh gained the mknod step, reading the major back from /proc/devices because it is
allocated dynamically.
